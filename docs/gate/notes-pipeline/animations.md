# Animations and Live Labs: the standard (binding)

The owner's words: *"more and more animations… it should feel like we are
visualising every possible thing."* Digital Logic has ≈ 4 scenes per lesson.
Every new subject must do better: **≥ 6 scenes per lesson, and every process
that has steps is animated.**

Two tools:

- **Viz scenes** (`:::viz{spec="name"}`): a step-by-step animated figure with a
  caption per step. They show *our* worked example evolving: a DFA consuming a
  string, a parse stack growing, a cache filling, a pipeline stalling.
- **Live Labs** (`:::lab{lab="…" tab="…"}`): interactive React tools where the
  reader types their own input (a regex, a grammar, an address trace) and
  watches the same process run.

---

## 1. Rules for every scene

1. **It teaches.** An animation explains an idea or a procedure step by step.
   No decorative motion. If a reader could learn the same thing from a still
   picture, make it `mode="static"`.
2. **One step = one idea.** Each step changes a small number of elements and
   its caption (≤ 400 chars, required) says *what happened and why*, as a
   teacher would. The caption is the text alternative; a screen-reader user
   must be able to follow the procedure from captions alone.
3. **Data comes from code.** Any scene that shows computed content (a
   transition table, a subset construction, FIRST/FOLLOW sets, an LR item set,
   a cache trace, a pipeline timing chart, a Booth step) is generated by the
   Python generator in `_checks/<s>/_viz_chN_lMM.py` from the same reference
   implementation the checks use. Never hand-type computed results.
4. **Colours are roles, never literals:** `tone`/`fill` from `VIZ_TONES`
   (`ink, muted, accent, subject, success, warning, danger, info`). Meaning is
   consistent across a subject:
   - `accent` = the thing happening *now* (current state, current symbol,
     current instruction);
   - `success` = accepted / hit / matched / done;
   - `danger` = rejected / miss / hazard / error;
   - `warning` = stall / conflict / needs attention;
   - `info` = lookahead, pointers, annotations;
   - `muted` = finished or inactive context.
5. **Phones.** Every scene wider than 360 px gets a `narrow` canvas (≤ 360 wide)
   with per-element `narrow` overrides, or `only: "wide" | "narrow"` variants.
   Check at 360 px: no text below 11 px, no overlaps, nothing cut off.
6. **Limits:** ≤ 400 elements, ≤ 60 steps per scene. A longer process gets two
   scenes (e.g. "building the LR(0) items" and "parsing with the table").
7. **Reduced motion and print:** the player shows the final frame with all
   captions listed; the scene must still make sense that way.
8. **Every scene has an `intro`** (what the first frame shows) and a `title`.
9. **Validate:** `node scripts/build-gate-notes.js --drafts` validates every
   scene against `client/src/viz/schema.ts` (`validateVizSpec`).

## 2. What the existing engine can draw

`client/src/viz/schema.ts`: `box`, `circle`, `node`, `text`, `arrow` (snaps to
element ids, can curve), `line` (polyline), `table` (header, highlighted
cells), `grid`, `bits` (bit strings with labels), `arc` (rings and sectors),
`gate` (logic-gate symbols). Steps patch any property (`tone`, `fill`,
`hidden`, `label`, `text`, `rows`, `x`/`y`…). **Today only opacity, fill and
stroke fade between steps (`viz.css`); position and size changes jump.** `arrow`
ends given as element ids are re-snapped every frame, so edges stay attached to
moving vertices. Smooth motion (gliding, morphing) is the engine job "motion"
below, and `dm.md` job E1.

## 3. Engine upgrades to build first (one PR each, before the chapters that need them)

These element types make the four subjects far clearer than boxes and
arrows. Build each one properly: type + validation in `schema.ts`
(`VIZ_ELEMENT_TYPES`, its interface, its checks, `VIZ_LAYOUT_KEYS` if it has
geometry), drawing in `VizScene.tsx` (+ `geometry.ts` for anchor points so
`arrow` can snap to it), styles in `viz.css` with tokens only, a test in
`tests/` that validates a sample scene and rejects bad ones, and a sample in
the dev gallery if one exists. Keep old scenes valid (no breaking changes).

**First, motion:** tween every numeric geometry property between frames (450 ms,
`requestAnimationFrame`, arrows recomputed per tick, none under reduced motion or
print). Full spec: `dm.md` job E1.

| Element | Needed by | What it draws | Key props |
|---|---|---|---|
| `state` | toc, cd (LR automata, lexers), coa (control FSM), dm (graphs optional) | An automaton state: circle with label, optional **double ring** for accepting, optional **start arrow**; arrows snap to its edge; self-loops supported | `cx, cy, r, label, accept?: boolean, start?: boolean` |
| `loop` | toc, cd | A self-loop arrow on a `state`, with a label, at an angle | `on: <state id>, angle, label` |
| `tape` | toc (TM, input string), cd (input buffer, lexeme pointers) | A row of cells with a **head** marker that moves (animated) and optional second pointer (`lexemeBegin`/`forward`) | `x, y, cell, cells: string[], head: number, head2?: number, headLabel?` |
| `stack` | toc (PDA), cd (parser stack, activation records), coa (call stack) | A vertical stack; pushes/pops animate; top marker | `x, y, w, cellH, items: string[], label?` |
| `wave` | coa (pipelines, bus/DMA timing, clocks) | Digital waveform rows (clock, signals) with time ticks; segments 0/1/X/data | `x, y, w, rowH, tick, rows: [{name, values: string}]` |
| `code` | cd (TAC, quadruples, assembly), coa (instruction sequences) | Monospace code lines with line numbers and a highlighted current line | `x, y, w, lineH, lines: string[], current?: number, marks?: number[]` |
| `tree` (optional; can be built from `node`+`arrow`) | cd (parse trees, ASTs, DAGs), toc (derivation trees) | Auto-laid-out tree from a nested spec; nodes revealed per step | `x, y, w, h, root: {label, children}` |

If you build `tree` with auto-layout, the layout must be deterministic and
done in the generator (Python) or in `geometry.ts` — never random.

## 4. Live Labs

- One lab per chapter at least, reused across the chapter's lessons via tabs.
- Pure logic in `labs/<name>Logic.ts` (no React), the UI in `labs/<Name>.tsx`.
- Register in `client/src/gate/notes/labs/index.ts` **and** `LAB_TABS` in
  `scripts/build-gate-notes.js` (same names, same tab ids).
- **Verified:** a Python reference in `_checks/<s>/` writes
  `lab_vectors_chN.json`; a Node test runs the TS logic on every vector and must
  agree exactly.
- **Step through, not just answer:** every lab has Step / Back / Play / Reset,
  shows the current step's explanation in words, and lets the reader edit the
  input. Speed control; Play is off under reduced motion.
- Input limits so nothing hangs (e.g. ≤ 12 NFA states, ≤ 20 grammar
  productions, ≤ 64 address trace items) with a clear message when exceeded.
- Built with the site kit: `ed-*` classes, design tokens, `data-ui` hooks; works
  in all ten themes, light and dark, keyboard only, 360 px wide.
- axe: 0 violations (light, dark, phone). Labels for every input; the live
  explanation region uses `aria-live="polite"`.
- Lazy-loaded (already handled by `index.ts`).

Note for Discrete Maths: `scripts/build-gate-notes.js` already lists
`relation-lab`, `hasse-lab`, `group-lab`, `counting-lab`, `recurrence-lab` and
`graph-lab` in `LAB_TABS`, but **they are not implemented in the client yet**
(`labs/index.ts` only has `truth-table` and `quantifier-lab`). Build each before
the chapter that embeds it.

## 5. Scene count and the check

Every lesson: ≥ 6 `:::viz` embeds (distinct scenes), and every procedure in
the lesson animated. Add a check `_checks/<s>/viz_density.py` that fails if any
lesson with `status: review|published` has fewer than 6 distinct viz specs, or
if any viz file is not used by some lesson.
