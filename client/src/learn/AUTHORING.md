# Writing a DSA course topic

This is the contract for every topic in the Nexora DSA course. The goal is the
best DSA course anywhere: a student who works through it end to end should be
able to clear the coding rounds at any company. That means **depth** (every
idea derived and proved, not asserted), **sight** (every algorithm animated
step by step, the way the machine actually runs it) and **practice** (dozens
of judged problems per topic, easy to genuinely hard, each with a complete
written solution in five languages, verified against the tests).

Read the Arrays and Complexity topics before writing — they set the voice.

---

## 1. Where everything lives

```
client/src/learn/content/dsa/<topic>/
  meta.ts          { ready, pages } — flip ready: true when done; pages = page count
  index.ts         assembleTopic({...}) — joins the parts below
  pages*.ts        lesson pages (split into several files, ~600 lines each)
  questions*.ts    quiz questions (graded on the page)
  algorithms*.ts   this topic's animations
  problems.ts      codeQuestions: one codeQ(...) per judged problem

scripts/learn/problems/<topic>.py          judged problems: statement, reference solve(), test generators
scripts/learn/solutions/<topic>/<slug>/    editorial.md, main.cpp, Main.java, main.py, main.js, main.c
src/learn/problems/<topic>.json            GENERATED by scripts/learn/build.py — commit it, never hand-edit
```

**Only touch files for your own topic.** Other topics are written in parallel;
shared files (syllabus.ts, the engine, assemble.ts, the Python lib) are frozen.
If you think the engine needs a change, work around it inside your topic.

`index.ts` looks like:

```ts
import { assembleTopic } from '../../assemble'
import { algorithms } from './algorithms'
import { intro, traversal /* … */ } from './pages1'
import { questions } from './questions'
import { codeQuestions } from './problems'

export default assembleTopic({
  id: 'linked-lists',
  title: 'Linked lists',
  blurb: '…one sentence listing what the topic covers…',
  pages: [intro, traversal /* … */],
  questions,
  codeQuestions,
  algorithms,
})
```

`assembleTopic` appends a "Practice problems" list to every page with the
coding problems whose `page` is that page — you do not write practice blocks
for coding problems yourself.

### Ids (prefix = your topic's prefix, e.g. `ll` for linked-lists)

| thing | pattern | example |
|---|---|---|
| page | kebab-case | `fast-slow-pointers` |
| quiz question | `<p>-q-<name>` | `ll-q-cycle-start` |
| animation | `<p>-<name>` | `ll-floyd` |
| judged problem (= its code question id) | `<p>-c-<name>` | `ll-c-merge-k` |

Prefixes: arrays `arr`, complexity `cx`, math `math`, recursion `rec`, bits `bit`,
strings `str`, binary-search `bs`, sorting-basic `sb`, sorting-advanced `sa`,
hashing `hash`, linked-lists `ll`, stacks `stk`, queues `que`, binary-trees `bt`,
bst `bst`, heaps `heap`, tries `trie`, segment-trees `seg`, graph-basics `gb`,
shortest-paths `sp`, mst-dsu `mst`, topo `topo`, advanced-graphs `ag`,
greedy `gr`, backtracking `bk`, dp-1 `dp1`, dp-2 `dp2`, dp-3 `dp3`,
string-algorithms `sal`, interview `int`.

## 2. Lesson pages

A page is `{ id, title, summary, minutes, blocks }`. Blocks:

| block | use |
|---|---|
| `{ t: 'md', md }` | prose. Markdown with `$inline$` / `$$display$$` KaTeX, tables, lists, `code` |
| `{ t: 'viz', algo, initial?, caption? }` | an animation player (`initial` overrides input defaults) |
| `{ t: 'code', title?, code: { cpp, java, python, js, c }, note? }` | the same code in tabs |
| `{ t: 'callout', kind, title?, md }` | `note` · `tip` · `warn` · `pitfall` · `insight` · `interview` |
| `{ t: 'complexity', title?, rows: [{ op, time, space?, note? }] }` | cost table |
| `{ t: 'steps', title?, items: [{ title, md }] }` | a numbered procedure / derivation |
| `{ t: 'check', ids, title? }` | inline quiz questions (by id) |

Markdown in template strings: indent freely (it is dedented), escape
backslashes in KaTeX (`\\log`, `\\times`), never use `${` inside text.

### What a page must contain

- **The why before the how.** Open with the problem the idea solves, a
  concrete example, and the naive approach and why it falls short.
- **Derivations and proofs.** State invariants explicitly and prove
  correctness (loop invariant, exchange argument, induction, contradiction —
  whichever fits). Derive complexities line by line, including recurrences.
  Never write "it can be shown".
- **At least one animation on every page that has an algorithm**, placed
  right after the idea is introduced, with a caption telling the learner what
  to watch for. Animate the *mechanism* (pointers moving, nodes relinking,
  the frontier expanding, the table filling with its dependency arrows), not
  just the result.
- **Code in all five languages** (C++, Java, Python, JavaScript, C) for every
  algorithm taught, idiomatic per language, compiling as written (wrap
  snippets in a function; show the struct/class definitions they need once
  per topic). For a structure C lacks (hash maps, dynamic arrays), write the
  minimal C version or say clearly what library you assume.
- **Worked examples** traced by hand, edge cases, and a `pitfall` callout for
  the bugs people really write. An `interview` callout with how the idea
  appears in interviews (typical phrasing, follow-ups, what the interviewer
  is checking).
- **A `complexity` table** for every structure/algorithm.
- **A `check` block** of 4–8 quiz questions at the end (and smaller ones
  mid-page when a concept needs checking before moving on).
- A final **cheatsheet page**: every pattern of the topic, when to use it,
  its complexity, the template code, and a recognition guide ("if the
  problem says X, think Y").

Tone: direct, warm, exact. Short paragraphs. Bold the one sentence per
section a student must remember. No filler, no "in this lesson we will".
Use books as references for rigour — CLRS, Sedgewick & Wayne, Skiena,
Kleinberg–Tardos, Competitive Programmer's Handbook (Laaksonen), cp-algorithms.
Write in your own words; do not paste copyrighted text.

### Size

A typical topic: **12–18 pages**, each 8–20 minutes of reading. Cover the
topic exhaustively — every standard technique, its variants, and the
advanced material interviews at top companies probe. Better too deep than
too shallow.

## 3. Animations (`algorithms*.ts`)

An animation **runs the real algorithm** on the learner's input and records a
frame at every meaningful step. Read `engine/types.ts`, `engine/tracer.ts`
and copy the shapes in **`engine/examples.ts`** (one example per view). The
Arrays topic's `src/learn/algorithms/arrays*.ts` show array animations.

```ts
export const llFloyd: Algorithm = {
  id: 'll-floyd',
  title: "Floyd's cycle detection",
  blurb: 'optional one-liner',
  inputs: [{ name: 'arr', label: 'Values', type: 'array', default: '3 1 4 1 5 9', maxLen: 10 }],
  random: () => ({ arr: list(rarr(rint(5, 9), 1, 9)) }),   // from src/learn/algorithms/util.ts
  legend: { found: 'meeting point' },                       // optional: rename a colour
  code: { pseudo: `…  // @step`, cpp: `…  // @step`, python: `…  # @step`, java, js, c },
  run: ({ arr }) => trace((t) => { … t.step('init', 'plain-language note', { vars }) … }),
}
export const algorithms = [llFloyd, …]
```

Structures (`t.array`, `t.list`, `t.tree`, `t.graph`, `t.hash`, `t.grid`,
`t.stack`, `t.queue`, `t.meter`, `t.print`) are snapshotted at every
`t.step(stepId, note, vars?)`. Rules:

- **Every `step` id must be tagged in every language's code** with a trailing
  `// @id` (or `# @id`). A line can carry several (`// @cmp,swap`). The check
  script fails otherwise. Provide `pseudo` always, and real code in at least
  cpp + python + java (all five is better).
- **Every frame has a note** — one plain sentence saying what is happening and
  *why*, with the actual values ("4 < 7, so the answer lies left of mid").
- Use roles consistently: `active` (looking at now), `compare`, `swap`
  (moving), `write`, `new`, `found`, `done`, `best`, `window`, `pivot`,
  `removed`, `dim` (out of play). Clear roles each step (`clear()`, `keep()`).
- Keep the default input small enough to watch (20–120 frames) and make it
  show the interesting cases (a collision, a relaxation that improves, a
  rotation). Give `random()` where inputs can be random; validate inputs and
  `throw new Error('friendly message')` for bad ones. Clamp sizes (`maxLen`,
  `min`, `max`).
- **Advanced animations are the point.** Show the machine: memory boxes and
  pointer rewiring for lists; the call stack beside the recursion tree;
  BFS frontier waves with distance badges; Dijkstra's relaxations with the
  priority queue alongside; DP tables filling with dependency arrows
  (`grid.arrow`); heap tree and array side by side; union-find forests
  re-parenting; segment trees lighting the covered nodes; KMP's failure
  function sliding the pattern. Combine structures in one animation whenever
  it helps (a tree + an array + a stack + variables).
- Aim for **15–30 animations per topic**: one per algorithm, plus variants
  and "why the naive way is slow" contrasts.

Preview while you work (no server or login needed):

```bash
cd client && npx vite --port 5300            # prints the real port if 5300 is busy
# then open http://localhost:<port>/viz-lab?topic=<topic>  or ?algo=<id>
node scripts/viz-shot.cjs http://localhost:<port> /tmp/shots <algo-id>@end <algo-id>@12
```

Look at the screenshots (`Read` the PNGs). Fix overlapping labels, unreadable
layouts, and frames whose note does not match the picture.

## 4. Quiz questions (`questions*.ts`)

Kinds (see `questions/types.ts`): `mcq`, `multi`, `numeric`, `text`, `order`,
`array` (predict the array), `fill` (fill blanks `[[0]]`, `[[1]]` in code),
`match`. Every question needs `id, topic, page, kind, difficulty, title,
prompt, explain` (+ `hint` when useful).

- **≥ 80 quiz questions per topic**, ≥ 5 per lesson page, using **at least six
  kinds**. Mix: concept checks, "trace this and predict the state", "spot the
  bug", complexity questions, "which technique fits this problem", and
  interview-style twists.
- Wrong options must be plausible (real misconceptions), never silly.
- `explain` teaches: why the answer is right **and** why the tempting wrong
  answer is wrong.
- Double-check every answer key by hand (or by running code). A wrong key is
  the worst bug a course can have.

## 5. Judged coding problems

### 5.1 The problem (`scripts/learn/problems/<topic>.py`)

```python
"""Linked lists — judged problems."""
import random
from lib import *  # add, fmt, ints, lines_of, arr_input, gen_queries, SIZE, LARGE, N_SPEC

def sol_reverse(s):
    v = ints(s); return fmt(v[1:1 + v[0]][::-1])

add('ll-c-reverse', 'Reverse a linked list', 'linked-lists', 'reversal', 900, ['linked list'],
    '<p>statement HTML…</p>', '<p>input spec HTML</p>', '<p>output spec HTML</p>', sol_reverse,
    samples=[arr_input([1, 2, 3])],
    edge=[arr_input([7]), arr_input([1, 1, 1])],
    rand=lambda: arr_input([random.randint(-10**9, 10**9) for _ in range(random.randint(1, SIZE))]),
    n_rand=7, large=None)
```

- `solve` is the **reference solution in Python**; every expected output comes
  from it. Make it obviously correct (brute force is fine for small inputs —
  if the brute force is too slow for the large test, write the efficient one
  carefully and cross-check it against a brute force on small random inputs
  inside the .py file with an `assert`).
- **The output must be uniquely determined** (the judge compares text
  exactly, ignoring trailing spaces/newlines). If several answers are valid,
  ask for a canonical one (smallest index, lexicographically smallest, sorted,
  count instead of list…). No floating-point output unless the value is
  exactly representable or you specify rounding that every language prints
  identically (prefer integers, fractions as `p/q`, or answers mod 10⁹+7).
- Input is stdin, output stdout. The statement is HTML (use `<code>`,
  `<sup>`, `<b>`, `<ul>`, `<pre>`), with exact constraints. State limits such
  that the intended complexity passes and a naive one would not.
- Tests: hand-written `edge` cases (min sizes, all-equal, negative, overflow
  bait, worst case for naive solutions) + random. Keep each problem's tests
  under ~200 KB (hard limit 800 KB); add one `large` test only when
  performance matters (n ≈ 2·10⁵ is plenty).
- `rating` is Codeforces-style: 800–1100 easy, 1200–1600 medium, 1700+ hard.

**How many:** **≥ 40 judged problems per topic** spanning the whole topic:
~30% easy, ~45% medium, ~25% hard. Include the classic interview problems of
the topic (the ones every FAANG prep list has — written in your own words
with your own tests), plus contest-style problems that need real insight.
Each lesson page with an algorithm should have 2+ problems.

### 5.2 The written solution (`scripts/learn/solutions/<topic>/<slug>/`)

`editorial.md` (Markdown + KaTeX, rendered in the Solve page's Solution tab):

```markdown
## Intuition
What to notice; how you would find the idea yourself. Start from brute force.

## Approach
The algorithm, step by step, with a small worked example.

## Why it works
The invariant / proof of correctness.

## Complexity
Time and space, derived.

## Pitfalls
Edge cases, overflow, off-by-ones — what fails hidden tests.

## Related
Variants and problems that use the same idea (optional).
```

`## Intuition`, `## Approach` and `## Complexity` are required (verify.py checks).

Solutions — all five, reading stdin and writing stdout, efficient enough for
the constraints, clean and commented like model answers:

| file | rules |
|---|---|
| `main.cpp` | C++17, `ios::sync_with_stdio(false); cin.tie(nullptr);`, `long long` where needed |
| `Main.java` | `public class Main`, fast input (`BufferedReader`/`StreamTokenizer` or a byte reader), `StringBuilder` for output |
| `main.py` | `sys.stdin` buffer read; iterative where recursion depth could exceed ~10⁴ (or raise the limit + use threading with a big stack) |
| `main.js` | Node: `require('fs').readFileSync(0, 'utf8')`, build output in an array and `join('\n')` |
| `main.c` | C11, `scanf`/`getchar`-based fast input, `long long`, free nothing fancy |

### 5.3 The code question (`problems.ts`)

```ts
import { codeQ } from '../../assemble'
const T = 'linked-lists'
export const codeQuestions = [
  codeQ(T, 'll-c-reverse', 'reversal', 'Reverse a linked list', 'easy', 'Reverse the list and print it.'),
  …
]
```

One per judged problem; `page` must match the problem's page.

### 5.4 Build and verify

```bash
python3 scripts/learn/build.py <topic>             # writes src/learn/problems/<topic>.json
python3 scripts/learn/verify.py <topic> -j 3       # compiles + runs all 5 solutions on every test
python3 scripts/learn/build.py --strict <topic>    # fails if any editorial/solution is missing
```

Every solution must pass every test in every language. Python and Java are
slower: if a correct Python/Java solution is close to 10 s locally on the
large test, shrink the large test — a correct O(n log n) solution must pass
comfortably in every language.
